## 1. Введение

В различных информационных системах одни и те же объекты могут классифицироваться
по-разному. Таксономии — иерархии классов, связанных отношениями «is-a» —
применяются в геоинформационных системах, например при обработке данных с беспилотных
летательных аппаратов для описания зданий, дорог, транспорта, растительности,
объектов инфраструктуры и других объектов. На практике достаточно часто встречается
необходимость взаимодействия между двумя системами, использующими разные классификаторы.
Таким образом возникает задача автоматического установления
соответствий между классами разных таксономий — *taxonomy alignment*, в более общем случае
известная в литературе как *ontology matching* (OM).

Ручное сопоставление таксономий — трудоёмкий и дорогой процесс, требующий
участия экспертов в предметной области. Автоматизация этого процесса, даже частичная, позволяет
сократить затраты труда и уменьшить количество ошибок, допускаемых оператором при ручной интеграции.

**Целью работы** является разработка прототипа системы, которая автоматически
устанавливает соответствия (маппинг) между узлами двух таксономий, оценивает
уверенность в найденных соответствиях и выявляет нарушения семантической
согласованности — как внутри каждой таксономии, так и в построенном отображении.

В рамках работы реализованы и сравнены между собой четыре подхода к задаче:

1. **Эмбеддинговый** — преобразование текстового описания узла в вектор
   с помощью bi-encoder-модели (sentence-transformers) и выбор кандидатов
   по косинусному сходству.
2. **Базовый строковый** (*StringEquiv*) — регистронезависимое сравнение меток узлов.
3. **LLM-подход** — бинарная классификация каждой пары
   «источник–кандидат» с помощью большой языковой модели в трёх
   представлениях и ансамблированием.
4. **Графовый (GNN)** — Siamese GraphSAGE, учитывающий структурное
   окружение узла через message passing.

Дополнительно исследована замена генеративного LLM-классификатора моделью
Jev, возвращающей вероятности эквивалентности (раздел 6.5).

Вторая половина работы — проверка согласованности. На графе каждой таксономии
и на построенном отображении проверяются циклы, ссылки на отсутствующие
родительские классы, достижимость классов от корня, дублирующиеся метки,
нарушения взаимной однозначности и подчинения, а также объявленная
несовместимость классов. Для семантических флагов измеряется качество фильтра
относительно эталона, а порог уверенности отдельно калибруется по схеме
leave-one-pair-out (раздел 6.4). Это частичная структурная проверка.

Качество оценивается стандартными метриками Precision, Recall и F1-score
на открытом датасете OAEI Conference track (семь онтологий, 21 эталонный
alignment, 258 загруженных классовых соответствий).


## 2. Обзор предметной области

### 2.1. Задача сопоставления онтологий

Ontology matching — задача нахождения семантических соответствий между
сущностями (классами, свойствами) разных онтологий. С 2004 года проводится
ежегодное соревнование OAEI (Ontology Alignment Evaluation Initiative),
в рамках которого участники решают задачу сопоставления на стандартизированных
наборах данных. Трек *Conference* включает семь онтологий по тематике научных
конференций (`cmt`, `confOf`, `Conference`, `edas`, `ekaw`, `iasted`, `sigkdd`) и 21 эталонное
попарное соответствие.

Рассматриваются только соответствия между классами (M1 в терминологии OAEI).
Соответствия между свойствами (M2) не рассматриваются; вариант M3 объединяет
классы и свойства. Обозначения вариантов оценки приведены в [13].

### 2.2. Существующие подходы

**Строковые методы.** Простейший подход — сравнение меток классов: точное
совпадение, расстояние Левенштейна, коэффициент Жаккара. В соревнованиях OAEI
регистронезависимое совпадение меток используется как официальный нижний порог
(baseline). Несмотря на простоту, на некоторых парах онтологий с пересекающейся
лексикой этот метод даёт высокие результаты.

**Эмбеддинговые методы.** Предобученные энкодеры (LaBSE, ruRoberta,
MiniLM) преобразуют текстовое описание узла в плотный вектор,
после чего близость узлов оценивается косинусным сходством. В отличие от
строковых методов, эмбеддинги способны улавливать семантическую близость
синонимичных, но лексически различных терминов.

**Графовые нейронные сети.** Подходы на основе GNN (GraphSAGE, GAT) кодируют
не только сам узел, но и его структурное окружение — родителей и потомков.
В GraphMatcher (Efeoglu, 2022) [6] графовые attention-сети используются
для учёта окружения концепта. Реализация настоящей работы — собственный
упрощённый Siamese GraphSAGE, не воспроизведение GraphMatcher.
Без порога он уступил MiniLM-базе; после калибровки порядок средних
обратный, но статистическое превосходство не проверено (раздел 6.3).

**LLM-подход (LLMs4OM).** В работе [LLMs4OM](https://arxiv.org/abs/2404.10317)
(Giglou et al., 2024) предложен фреймворк использования больших языковых моделей
для сопоставления онтологий. Для каждого узла исходной таксономии эмбеддинговая
модель отбирает топ-$k$ ближайших кандидатов из целевой таксономии, после чего
LLM для каждой пары «источник–кандидат» принимает бинарное решение: «соответствует»
или «не соответствует». В статье сравниваются три представления концепта:
C — основные характеристики, CP — с родительским контекстом,
CC — с дочерним контекстом. В каждом варианте выполняются классификация
и постобработка: фильтр $S_{llm} > 0.7$, высокоточный шаг
$S_{ir} > 0.9$ и ограничение кардинальности.
Ансамбль представлений — дополнение настоящей работы, а не часть
оригинального LLMs4OM; отличия реализации перечислены в разделе 4.3.
Близкая схема бинарной LLM-оценки пар есть и в OLaLa
(Hertling, Paulheim, 2023) [12].

### 2.3. Обоснование выбора подходов

Строковый метод — обязательная точка отсчёта, не гарантированная нижняя
граница качества: более сложный метод может ему уступать.
Эмбеддинги позволяют проверить семантическое сопоставление без внешнего API,
LLM — оценку кандидатов по текстовому контексту, GNN — обучение представлений
с учётом графа. Это сравнение доступных реализаций; современность модели
сама по себе не обосновывает её точность или научную новизну.


### 2.4. Проверка согласованности отображений

Второй вопрос темы относится к отдельной линии работ — проверке *согласованности*
отображения, а не только его качества по F1.

**Логическая несовместимость.** Две таксономии могут быть непротиворечивы по
отдельности, а их объединение вместе с отображением — стать логически
несовместимым. Система LogMap [7] не только строит отображение, но и
обнаруживает такие несовместимости и *ремонтирует* отображение, отбрасывая
связи-причины. В настоящей работе ремонт не выполняется: проверки только
обнаруживают нарушения и позволяют измерить их число и локализацию.

**Принцип консервативности.** Отображение нарушает консервативность, если
меняет отношение подчинения между классами: класс становится потомком другого
класса, хотя до отображения таковым не был. Обнаружение и исправление таких
нарушений исследовано в [8]; проверка подчинения в разделе 6.4.2 — упрощённый
вариант этой идеи: она работает с отношениями между узлами и объявленной
несовместимостью, без логического вывода и без ремонта.

**Место в общей картине.** Проверка и объяснение соответствий как отдельная
задача разобраны в монографии [9]; из неё в настоящей работе используются
структурная и декларативная части (граф подчинения, объявленная
несовместимость), а логическая — только как направление дальнейшей работы
(раздел 7.3).

## 3. Постановка задачи

### 3.1. Формализация

**Вход.** Две таксономии $S$ (source) и $T$ (target). Каждая таксономия —
направленный ациклический граф (DAG), где узлы — классы, а рёбра —
отношения «is-a». Каждый узел имеет имя (label) и, опционально, список
атрибутов. Допускается множественное наследование (т.е. каждый узел может
иметь несколько родителей).

**Выход.** Множество троек $(s,t,c)$: исходный класс, целевой класс и оценка.
У эмбеддингов и GNN $c$ — косинусное сходство с диапазоном $[-1,1]$,
а не вероятность. У генеративной LLM — запрошенная самооценка из $[0,1]$;
текущая реализация не проверяет её диапазон. Jev возвращает вероятность
ответа «да» из $[0,1]$, проверяемую при загрузке журнала.
Единый смысл шкалы `confidence` между методами не предполагается.
Для основных предсказаний применяется ограничение 1:1: каждый узел
сопоставляется не более чем одному узлу другой таксономии.
Это частичное инъективное отображение, а не требование сопоставить все классы.
`argmax` в абляции и общий StringEquiv могут допускать повтор цели;
в сохранённых StringEquiv-результатах таких коллизий нет.

**Ограничения.** Оценка проводится на открытых данных OAEI.
Внешние API допустимы: OpenAI-совместимый интерфейс для генеративных LLM,
OpenRouter Decisions API для Jev.

**Выход (проверка согласованности).** Отчёт $V$ — множество нарушений, каждое
из которых относится либо к таксономии, либо к паре отображения. Внутри
таксономии проверяются: цикл в отношении «is-a», совпадающие метки у разных
классов, общий потомок двух объявленных несовместимых классов (включая
случай несовместимого предка), ссылка на отсутствующего родителя и отсутствие пути
к корневому классу. В отображении проверяются: нарушение инъективности 1:1,
пара, противоречащая объявленной несовместимости, и несохранение подчинения
(в том числе отсутствие нужной связи в цели, а не только её инверсия).
Низкая уверенность — отдельный сигнал постобработки для Human-in-the-Loop.

### 3.2. Данные

Используется трек Conference соревнования OAEI 2025. В треке 16 онтологий, но
эталонные соответствия размечены только для семи из них — эти семь и взяты:

| Онтология  | Число узлов |
|------------|:-----------:|
| cmt        | 29          |
| confOf     | 38          |
| conference | 59          |
| edas       | 103         |
| ekaw       | 73          |
| iasted     | 140         |
| sigkdd     | 49          |

Эталонные соответствия (reference alignments) варианта ra1 доступны для всех
21 попарной комбинации этих семи онтологий, то есть для полного пространства пар.

Сырые файлы эталона содержат 305 связей. Из них 46 — соответствия между
**свойствами** (например, `cmt#writePaper` ↔ `confOf#writes`), а не классами;
они отброшены, поскольку работа ограничена таксономиями классов. Остаётся 259
классовых связей, до модели доходит 258: в `cmt-conference.rdf` источник
`cmt#Conference` указан дважды (на `Conference_volume` и на `Conference`), а
загрузчик хранит одно соответствие на источник и сохраняет последнее. Поэтому
инъективным (1:1) является *предсказание* матчера, а не сам эталон: в нём
встречаются и связи вида «многие к одному» (`confOf-ekaw.rdf`: два источника на
`ekaw#Student`).
При эталоне n:m инъективное предсказание 1:1 может не достичь полного recall;
это ограничение загрузки и постановки, а не обязательно ошибка матчера.

Используется crisp-вариант ra1, не uncertain-эталон с экспертными
оценками уверенности. Организаторы публикуют эти варианты отдельно [13].
Прямое сравнение со сводными числами OAEI требует согласования эталона,
состава сущностей, кардинальности и усреднения: здесь загрузчик изменяет
ra1-M1, предсказания ограничены 1:1 и основная метрика — macro F1,
тогда как официальная сводка использует micro-усреднение.
Упрощённая структурная проверка не воспроизводит официальную оценку
логической согласованности и консервативности.

Для тестирования на контролируемых условиях дополнительно сгенерированы
синтетические вариации таксономии cmt (29 узлов):

- **exact** — точное копирование с изменёнными идентификаторами;
- **synonym** — частичная словарная замена имён, без разбиения CamelCase;
- **structural** — переподчинение одного листа более высокому предку;
- **attribute** — изменение имеющихся атрибутов и добавление их узлам без атрибутов.

### 3.3. Метрики

Качество сопоставления оценивается стандартными метриками:

- **Precision** = $\frac{TP}{TP + FP}$ — доля правильно предсказанных
  соответствий среди всех предсказанных.
- **Recall** = $\frac{TP}{TP + FN}$ — доля найденных эталонных соответствий.
- **F1-score** = $2 \cdot \frac{P \cdot R}{P + R}$ — гармоническое среднее Precision и Recall.
  Внутри одной пары TP, FP и FN считаются суммарно по её предсказаниям, а по
  21 паре значения усредняются **macro** (невзвешенно по парам) — именно это
  число приводится ниже. Для сравнения в разделе 6.4.4 дано и
  micro-усреднение (суммарные TP, FP и FN по всем парам).

Соответствие считается истинно положительным (TP), если предсказанная
пара $(s, t)$ присутствует в эталонном отображении.

Дополнительно используются метрики проверки согласованности и сравнения
подходов:

- **число нарушений по видам** — отдельно по целостности таксономий и по
  согласованности отображений;
- **precision и recall флага** — доля ошибочных пар среди помеченных и доля
  помеченных среди всех ошибочных: показывают, работает ли проверка как
  фильтр или только как отчёт;
- **F1 как функция порога уверенности** — для калибровки постобработки; порог
  выбирается по схеме leave-one-pair-out: подбирается на остальных парах и
  применяется к отложенной, поэтому оценка не подогнана под неё;
- **recall@$k$ кандидатов** — доля эталонных пар, попавших в кандидатное
  множество размера $k$; это верхняя граница полноты для LLM-подхода;
- **парный bootstrap и критерий Уилкоксона** по 21 паре — сравнение подходов,
  потому что средние по парам сильно различаются и одно среднее их не описывает.


## 4. Выбор метода

### 4.1. Эмбеддинговый подход

**Модели.** Четыре энкодера используются через библиотеку sentence-transformers:

| Модель          | Размерность | Специфика                                  |
|-----------------|:-----------:|--------------------------------------------|
| LaBSE           | 768         | Мультиязычная, хороша для смешанных данных |
| MiniLM-L6-v2    | 384         | Лёгкая, быстрая                            |
| ruRoberta-large | 1024        | Русскоязычная, наибольшая размерность      |
| rubert-base     | 768         | Компактная русскоязычная                   |

Идентификаторы моделей: `sentence-transformers/LaBSE`,
`sentence-transformers/all-MiniLM-L6-v2`, `ai-forever/ruRoberta-large`
и `DeepPavlov/rubert-base-cased`.
Источник — `EMBEDDING_MODELS` в `src/runners/compare.py` и поля `model` кэша.

**Процесс.** Строится текст узла и полная матрица косинусного сходства
эмбеддингов двух таксономий. В абляции MiniLM с `argmax` имя класса
(`name_only`) даёт средний F1 0.309 против 0.211 у полного описания.
Совместное добавление несовместимостей и комментария ухудшает результат;
отдельные эффекты этих компонентов не разделены (раздел 5.3).

В сравнительных таблицах применяется `greedy_injective`:
все элементы матрицы просматриваются по убыванию оценки, при равенстве —
по идентификаторам источника и цели. Пара принимается, только если оба узла
ещё свободны. Без порога получается $\min(|S|,|T|)$ пар.
Это не удаление коллизий из одного ближайшего кандидата каждого источника:
жадный отбор может выбрать другую цель, если ближайшая уже занята.
`argmax` и `dedupe_by_target` исследованы отдельно.

Демонстрационный `match_with_threshold` не удаляет пары: он помечает низкие
оценки и близких конкурентов для ручного разбора. Пороговая фильтрация
в абляции выполняется при отборе матрицы, а в калибровке — по сохранённым
инъективным предсказаниям (раздел 6.4.4). Параметр $k$ относится к retrieval.

**Обоснование.** LaBSE показал наибольший средний результат (F1 = 0.360 по
21 паре), MiniLM-L6-v2 (384-мерная) уступает ему на 0.011 (0.349), и это
различие парный тест не подтверждает: восемь побед, три поражения, десять
ничьих, сырое $p = 0.32$ (диагностика вне семейства Холма).
MiniLM работает быстрее и используется в LLM-пайплайне для отбора кандидатов;
русскоязычные модели уступают на английских данных без порога, но не после калибровки.

### 4.2. Базовый строковый подход (StringEquiv)

**Метод.** Используется `node.name.strip().lower()`: совпадающие обработанные
имена дают пару с оценкой 1.0; при нескольких целях выбирается минимальный
идентификатор. Общий алгоритм не запрещает разным источникам выбрать одну
цель, но в сохранённых 21 отображении таких коллизий нет.

**Обоснование.** Это адаптация идеи официального StringEquiv, который
сравнивает нижнерегистровые локальные имена сущностей [13]. Здесь имена
предварительно обработаны OWL-парсером, поэтому реализация не объявляется
точной копией официального baseline. Метод силён при общей лексике:
`conference ↔ confOf` даёт F1 = 0.737. Его превосходство над более сложным
методом — допустимый экспериментальный результат.

### 4.3. LLM-подход

**Фреймворк.** Реализована адаптация LLMs4OM [1], а не точное воспроизведение:
описание для retrieval не следует режиму промпта; одно обращение
классифицирует сразу кандидатов одного узла, а не одну пару;
высокоточный шаг $S_{ir} > 0.9$ не реализован.
Ансамбль представлений добавлен в настоящей работе. Вместо вероятности
токена используется самооценка модели в JSON; для ошибок есть резервное
решение, происхождение которого не сохранено в историческом кэше.

**Представления узлов.** Для каждого узла строится три текстовых представления:

- **C (Concept):** имя узла, а также его атрибуты, комментарий и объявленные
  несовместимости, если они есть в онтологии;
- **CP (Concept-Parent):** то же плюс кратчайшая цепочка предков узла;
- **CC (Concept-Children):** то же, что C, плюс имена непосредственных
  дочерних узлов.

**Процедура.** Для каждого узла источника $s$ выполняются следующие шаги:

1. В варианте MiniLM отбираются топ-$k=5$ целей по полным описаниям,
   независимо от C/CP/CC в промпте. BM25 и гибридный retrieval описаны
   в разделе 5.4; у гибрида эмбеддинговая часть использует `name_only`.
2. Алгоритм запускается независимо в трёх вариантах (C, CP, CC), каждый раз
   с промптом, содержащим соответствующую информацию об узлах. Для каждой
   пары $(s, t)$ LLM принимает бинарное решение о соответствии.
3. Каждый режим отдельно оставляет положительные решения с самооценкой
   **строго выше 0.7**, затем выполняет `greedy_injective`.
   При конфликте выбирается большая оценка, при равенстве — идентификаторы.
4. ENS голосует по уже выбранным соответствиям режимов, не по всем сырым
   «yes»: пара должна присутствовать минимум в двух выходах.
   Оценки проголосовавших усредняются, затем повторяется отбор 1:1.
   Порог числа голосов не уменьшается при отсутствии режима;
   штатная пересборка требует все три кэша. Новые API-запросы не нужны.

**Использованные модели.** Эксперименты проведены с двумя LLM:

- `gpt-4.1-mini` — через OpenAI-совместимый API, с поддержкой
  структурированного вывода (`response_format: json_schema`);
- `deepseek-v4-flash` — через API DeepSeek; без `json_schema`,
  JSON-формат задаётся промптом.

Локальные Qwen3.5-0.8B и Llama-3.2-1B-Instruct использовались
для неформальных качественных проб на RTX 3090. Полный воспроизводимый
бенчмарк для них не сохранён; вывод о качестве малых моделей в целом не делается.

**Параллелизм и отказоустойчивость.** До 10 рабочих потоков.
Для ошибок, распознанных как 429 или сетевые, предусмотрены неограниченные
повторы с экспоненциальной задержкой до 15 секунд. При неповторяемом
исключении выбирается первый кандидат текущего ретривера с оценкой 0.75;
у BM25 это не обязательно эмбеддинговый кандидат.
Три одинаковые начальные ошибки до первого успеха прерывают прогон.
Некорректный JSON сам по себе даёт пустое решение, а не fallback.

Уверенность LLM — самооценка в JSON-ответе, а не вероятность токена
«yes/no» из статьи. При резервном выборе первого кандидата задаётся 0.75.
Кэш не сохраняет происхождение таких ответов, поэтому долю fallback нельзя
восстановить: значение 0.75 само по себе не доказывает резервную обработку.

**Обоснование.** LLMs4OM — опубликованная схема отбора кандидатов
и бинарной оценки пар, позволяющая исследовать текстовый контекст.
Наличие объяснения в ответе не доказывает правильность решения;
уникальность или превосходство этого фреймворка не заявляются.

### 5.2. Подготовка данных

OWL разбирается через `owlready2`: имя — первая `rdfs:label`, а при её
отсутствии локальное имя класса с заменой подчёркиваний пробелами.
Сохраняются явные связи именованных классов, комментарии и объявленная
несовместимость. Атрибутами становятся только прямые ограничения свойств
в `equivalentClass`; ограничения `subClassOf` и вложенные OWL-выражения
не интерпретируются. JSON — упрощённая модель, не без потерь сохранённая онтология.

Для отдельного синтетического LLM-эксперимента используется `cmt` (29 узлов).
Генератор `src/data_loader.py` также применяется к онтологиям обучающих
пар GNN (раздел 5.6), а не только к `cmt`. Реализованы четыре сценария:

- **exact**: полное копирование узлов с добавлением суффикса `_V1` к идентификаторам;
- **synonym**: частичная замена имён по словарю, без разбиения CamelCase;
- **structural**: один лист переподчиняется более высокому предку, если такой лист есть; к ID добавляется `_STR`;
- **attribute**: имеющиеся атрибуты переименовываются или удаляются, а части узлов без атрибутов добавляется атрибут.

### 5.3. Эмбеддинговые эксперименты

Эмбеддинговые эксперименты проведены на всех 21 парах OAEI Conference
track для четырёх моделей: LaBSE, MiniLM, ruRoberta-large и rubert-base.
В абляции MiniLM на 21 паре при правиле `argmax` наибольший средний F1
даёт имя класса. Источник — `results/embedding-modes-MiniLM-canonical.json`
(`make ablation`); вывод ограничен этой моделью, описаниями и правилом.

| Описание узла                                                          | F1        |
|------------------------------------------------------------------------|:---------:|
| `name_only` — только имя                                               | **0.309** |
| `name_path` — имя и цепочка предков                                    | 0.303     |
| `name+attributes` — имя и атрибуты                                     | 0.280     |
| `name+disjoint+comment` — имя, атрибуты, несовместимости и комментарий | 0.190     |
| `full` — имя, цепочка, атрибуты, несовместимости и комментарий         | 0.211     |

Цепочка предков меняет F1 с 0.309 до 0.303; описание с атрибутами даёт 0.280.
Добавление к нему совместного блока несовместимостей и комментария даёт 0.190.
Отдельные эффекты этих двух компонентов не изолированы. Конкуренция имён
несовместимых классов — возможное объяснение, не установленная причина.
Кроме состава контекста меняется формат: `name_only` не содержит префикса
`Name:`, который есть у составных описаний.

**Правило отбора пар.** Тот же матчер при разном правиле даёт разные числа, и
различие больше, чем эффект выбора модели (там же):

| Правило отбора                                       | Средний F1 | Предсказаний на пару |
|------------------------------------------------------|:----------:|:--------------------:|
| `argmax` — ближайший узел на каждый исходный         | 0.309      | 57.9                 |
| `greedy_injective` — жадно-инъективное 1:1           | 0.349      | 47.0                 |
| `dedupe_by_target` — удаление коллизий из argmax-пар | 0.496      | 25.9                 |
| `greedy_injective` с порогом 0.50                    | 0.559      | 22.8                 |
| `greedy_injective` с порогом 0.70                    | 0.660      | 11.5                 |

**Гиперпараметры.** Канонический эмбеддинговый кэш использует
`name_only` и глобальный `greedy_injective` по всей матрице без порога.
В абляции порог 0.50 или 0.70 применяется до отбора;
LOO-калибровка раздела 6.4.4 фильтрует уже сохранённые пары.
`match_with_threshold` в демонстрации помечает неуверенные ближайшие
соответствия, но не отбрасывает их и не является этим калибровочным фильтром.

### 5.4. LLM-эксперименты

LLM-подход протестирован на всех 21 паре трека Conference. Различаются
две сущности: модель-классификатор и ретривер, который отбирает кандидатов.

**Модель-классификатор:**

1. **gpt-4.1-mini** — structured output (`json_schema`), 10 параллельных
   рабочих потоков;
2. **deepseek-v4-flash** — без `json_schema` (JSON задаётся промптом),
   10 рабочих потоков; на этой модели сравниваются все три ретривера.

**Ретривер кандидатов** (для каждого узла исходной таксономии отбираются
кандидаты из целевой, классификатор вызывается только по ним):

1. **MiniLM** — пять кандидатов по полным описаниям независимо от промпта.
2. **BM25** — до пяти кандидатов по токенизированным именам с положительным
   счётом BM25. Источники без кандидатов не отправляются в API и не получают матч.
3. **Гибридный** — пять MiniLM-кандидатов по `name_only` и до пяти новых
   положительных BM25-кандидатов по именам; вместе не более десяти.

Таким образом меняются и алгоритм, и эмбеддинговое описание, и бюджет
кандидатов; отдельный эффект retrieval при одинаковых условиях не изолирован.
Представления классификатора C/CP/CC определены в разделе 4.3:
C содержит также атрибуты, комментарий и несовместимости, не только имя.
Режимы и ENS сохранены в `results/`, сводка — `results/comparison.xlsx`.

Неформальные локальные пробы не входят в итоговые численные сравнения.

### 5.5. Синтетические данные

LLM (`deepseek-v4-flash`, режим `concept`, 29 узлов `cmt` на сценарий)
протестирован на четырёх синтетических сценариях; те же числа, что ниже,
машиночитаемо лежат в артефакте `results/synthetic.json`, который пишет
сам раннер (`src/runners/llm.py`):

| Сценарий     | P     | R     | F1    | Совпадений |
|--------------|------:|------:|------:|-----------:|
| `exact`      | 1.000 | 0.966 | 0.982 | 28/29      |
| `synonym`    | 1.000 | 0.517 | 0.682 | 15/29      |
| `structural` | 1.000 | 1.000 | 1.000 | 29/29      |
| `attribute`  | 1.000 | 0.966 | 0.982 | 28/29      |

В режиме C `structural` дал 29 соответствий из 29. Иерархия не включается
непосредственно в промпт C, но используется при full-retrieval.
Для частичной словарной замены `synonym` получено 15 из 29;
часть исходных имён, в том числе CamelCase, остаётся неизменной.
Артефакт хранит итоговые метрики, но не все кандидаты и причины решений:
пропуски нельзя приписать только незнанию синонимов. Сопоставимые снимки
входов и промежуточных решений прежнего прогона не сохранены, поэтому
расхождения с прежними числами не объясняются здесь только недетерминизмом.

### 5.6. GNN-эксперименты

Siamese GraphSAGE оценён на всех 21 парах по `pair-loo`.
На каждом фолде используются 20 реальных пар и синтетические записи
только для онтологий, выступающих источниками оставшихся обучающих пар:
обычно для шести, в фолде `iasted ↔ sigkdd` — для пяти.
Три семени и четыре сценария дают двенадцать именованных записей
на исходную онтологию: всего 92 обучающие тройки, в исключительном фолде — 80.
Число номинальных положительных примеров — 3867–5558.
Это не независимые новые онтологии: `exact` и `synonym` повторяются между
семенами, а изменения атрибутов не входят в признаки GNN.
Самопроверка генератора контролирует сценарные изменения и уникальность
имён, а не независимость входов модели.

Было опробовано несколько архитектурных вариантов: двухслойный GNN
с bottleneck-сжатием (384→256→128→64→32), однослойный с residual
connection (384→384), и линейная проекция без графовых свёрток
(LinearSiamese). В выводах используются только те варианты, которые
сохранены в кэше и снабжены конфигурацией в записях: основной протокол
leave-one-pair-out, вариант без синтетической аугментации, вариант
без графовых свёрток (`LinearSiamese`), протокол с полностью отложенной
онтологией и базовый уровень по предобученным признакам MiniLM под тем же правилом
отбора 1:1. Команды — `make gnn`, `gnn-ontology`, `gnn-baseline`.
Правило отбора пар во всех прогонах зафиксировано (`greedy_injective`):
без этого сравнение подходов не имеет смысла (раздел 6.3).

### 6.2. Анализ результатов

**StringEquiv — сильный baseline.** Средний F1 — 0.663.
На `cmt ↔ edas` точные имена дают 1.000, на `confOf ↔ sigkdd` — 0.800,
на `conference ↔ confOf` — 0.737. Метод не находит соответствие без
совпадения обработанных имён, но это не делает его слабым в среднем.

**LLM полезна на отдельных парах.** На `cmt ↔ conference` gpt-4.1-mini ENS
даёт 0.667 против 0.375 у строк; гибрид на `cmt ↔ sigkdd` — 0.889
против 0.750, на `edas ↔ ekaw` — 0.743 против 0.385.
Это примеры разных фиксированных конфигураций, не оценка правила выбора
лучшей модели под каждую пару. Сочетание LLM и StringEquiv не измерялось.

**Ретривер и агрегация должны быть зафиксированы.** Различия средних по
ретриверам и различия C/CP/CC — разные срезы эксперимента, не изоляция
причин качества. ENS не выбирает режим по эталону, но снижение шума
генерации его применением не измерено.

**DeepSeek против gpt-4.1-mini.** С одним MiniLM-ретривером ансамбли дают
0.602 и 0.575; парный тест именно этих ансамблей не сохранён.
Для средних по C/CP/CC (0.559 и 0.545) различие не подтверждено:
сырое $p = 0.865$, Holm $p = 1.00$ (раздел 6.4.6).

**Повторные прогоны показывают недетерминизм, а не шум среднего.**
На `cmt ↔ confOf` три запуска режима C с гибридным ретривером
deepseek-v4-flash дали 0.750, 0.533 и 0.625 (размах 0.217).
Повторы только на двух парах не оценивают вариативность среднего по
21 паре или ансамбля и не позволяют объявить различия 0.04–0.06 шумом.
Сравнения по кэшу проверяются парными тестами (раздел 6.4.6).

**Эмбеддинги конкурентоспособны, если калибровать порог уверенности.**
Без порога LaBSE даёт F1 0.360. Глобальный жадный отбор выдаёт
$\min(|S|,|T|)$ пар на каждую пару онтологий: всего 986 предсказаний
при 258 эталонных. Pooled precision — $215/986 \approx 0.22$,
macro precision — 0.234. LOO-отсечение поднимает F1 до 0.636 у LaBSE
и до 0.677 у ruRoberta-large (precision 0.809), лучшего среднего среди
эмбеддинговых конфигураций. Без порога порядок этих моделей обратный:
0.299 у ruRoberta-large против 0.360 у LaBSE.
Качество зависит от постобработки, а вывод абляции описаний относится
к MiniLM с `argmax`, не ко всем моделям и задачам.

**Ансамбль (ENS).** Мажоритарное голосование трёх режимов («не менее двух из
трёх»), дополнительных обращений к API не требует. Относительно среднего по
режимам он поднимает результат у обеих конфигураций с MiniLM-ретривером:
deepseek 0.559 → 0.602, gpt-4.1-mini 0.545 → 0.575 (таблица раздела 6.1,
`results/llm-aggregations.json`). Это сравнение агрегаций одного сохранённого
прогона, а не измерение снижения шума генерации. Протокол отличается от
LLMs4OM способом объединения режимов и оценочным протоколом.

### 6.3. Графовые нейронные сети (отрицательный результат без порога)

Дополнительно реализован и протестирован графовый подход на основе
Siamese GraphSAGE (Hamilton et al., 2017). Целью было установить,
помогает ли учёт структурного окружения узла (родителей и потомков)
улучшить качество сопоставления относительно чистого BERT.

**Архитектура.** Однослойный GraphSAGE с residual-связью: 384-мерные
эмбеддинги MiniLM на входе, 384-мерные векторы на выходе, без
bottleneck-сжатия (`in_dim = hidden_dim = out_dim = 384`, один слой,
`linear = false`). Две таксономии кодируются общей (Siamese) GNN, после
чего считается матрица косинусного сходства (векторы перед умножением
L2-нормируются). Модель обучается с функцией потерь MSE: косинусное
сходство → 1.0 для положительных пар (эталонные соответствия), → 0.0 для
отрицательных (случайно выбранные несоответствующие пары, 3 отрицательных
на одно положительное). Параметры прогона записаны в самих записях
(`config` в `results/gnn/*.json`): `fold_mode=pair-loo`, `seed=42`,
60 эпох, три синтетических семени, `linear=false`.

Рёбра «родитель–ребёнок» для message passing сделаны неориентированными,
добавлены self-loops; матрица нормируется как $D^{-1/2}AD^{-1/2}$.
Слой отдельно преобразует признаки узла и `adj @ x` через Linear/ReLU,
конкатенирует их, снова преобразует, добавляет residual и dropout.
После слоя применяется выходная линейная проекция.
Следовательно, направление «is-a» не кодируется как отдельный тип ребра.

**Протокол обучения.** `pair-loo` исключает эталонные метки одной пары,
но обе её онтологии остаются концами других обучающих пар.
Синтетические тройки строятся по источникам обучающих пар (раздел 5.6);
повторяющиеся варианты увеличивают число обучающих примеров, но не число
независимых концептов. Это оценка на уже виденных онтологиях,
не ontology-disjoint проверка переноса.

**Гиперпараметры.** Признаки — MiniLM по имени узла (384-мерные, режим
`name_only`); 384 → 384, один слой, без bottleneck, `linear = false`.
Оптимизатор — Adam; `epochs=60`, `lr=0.003`, `dropout=0.5`,
`weight_decay=0.0001`, `neg_ratio=3`, `seed=42`.
В `config` сохранены параметры, `fold_mode` и метка конкретного фолда;
число завершённых фолдов указано в `results/gnn-protocols.json`.
Основные прогнозы и `match_pairs` находятся в `results/gnn/*.json`,
оценённые веса — в `fold-<k>.pt`. Остальные протоколы перезаписывают
те же имена прогнозов; их сводки сохранены отдельно.
`results/gnn/model.pt` — диагностическая модель `--train` на всех парах,
не leave-one-out checkpoint. Финальная потеря в опубликованных артефактах
не сохранена и здесь не приводится.

**Протоколы.** Кроме основного прогона (leave-one-pair-out) посчитаны
контрольные варианты; каждый запускается своей целью Makefile (`make gnn`,
`gnn-ontology`, `gnn-baseline`) и сохраняет записи с полем `config`.
Сводка по всем пяти протоколам — в `results/gnn-protocols.json`
(команда, конфигурация, число фолдов, макро-метрики, F1 по каждой паре):

### 6.4. Проверка согласованности и калибровка постобработки

Проверки реализованы в `src/consistency.py`, запускаются целью
`make consistency` и работают на двух уровнях: целостность отдельной
таксономии и согласованность построенного отображения. Отбор кандидатов
и порог уверенности исследуются там же, потому что проверка одновременно
служит постобработкой — её эффект измеряется, а не декларируется.

Проверено 483 записи канонического кэша: по 21 записи для четырёх
эмбеддинговых моделей, GNN, его базы и StringEquiv; для каждого из четырёх
LLM-вариантов — по 84 записи (21 пара × C/CP/CC/ENS).
Во всех записях есть `match_pairs`, и пересчёт F1 совпадает с сохранённым
значением. Отдельный эксперимент Jev хранится вне этого кэша и рассмотрен
в разделе 6.5; его результаты не входят в эти 483 записи.

Источник таблицы — `results/consistency/taxonomies.json`; глубина относится
к сохранённой модели таксономии, а не к полной системе OWL-аксиом.


Всего в семи онтологиях 491 класс; реализованные проверки не нашли нарушений.
Это частичная структурная проверка, а не доказательство OWL-согласованности.
Многокорневость (от шести до 20 классов верхнего уровня) нарушением не
считается: парсер не связывает верхние классы с `owl:Thing`.
Корни определяются автоматически как узлы без объявленных родителей;
недостижимым считается класс без пути ни к одному такому корню.
В конечном DAG с корректными ссылками такой путь существует по построению.
Поэтому эта проверка уточняет последствия циклов и оборванных ссылок,
но не является независимым условием целостности и не проверяет достижимость
от заранее заданного предметного корня.

Проверка объявленной несовместимости ищет не только несовместимого предка
и потомка, но и класс, наследующий сразу от двух несовместимых предков.
Такой класс потенциально невыполним; это не доказательство противоречивости
онтологии целиком, поскольку OWL допускает пустые классы.

Чтобы проверки не были пустыми по построению, у раннера есть самопроверка
(`--selftest`): на заведомо испорченной таксономии, где есть цикл, дубликат
метки, несовместимость класса с собственным потомком, оборванная ссылка на
родителя и компонента без корня, срабатывают все виды проверок (пять), а на
здоровой таксономии отчёт остаётся пустым.

Совпадение меток — предупреждение для оператора, а не логическая ошибка:
разные классы могут законно иметь одинаковое название.

Для эмбеддинговых подходов, GNN и StringEquiv суммы взяты по 21 паре, для

ансамбль, 84 записи). «Пар предсказано» — число матчей в отображении,
«помечено матчей» — сколько из них отбросил бы фильтр по семантическим
нарушениям (объединение по видам).

Проверка «1:1» считает перегруженные группы с обеих сторон:
источник с несколькими целями или цель с несколькими источниками.
В каноническом кэше после постобработки таких групп нет.
У эмбеддинговых подходов и GNN это глобальный жадный отбор, у LLM —
отбор внутри пайплайна, у StringEquiv на этих данных коллизий не возникло.
Нулевая колонка подтверждает свойство сохранённых отображений, а не их
семантическую правильность.

Проверка различает подходы там, где средний F1 их почти не различает.
Семантические нарушения у эмбеддинговых подходов и GNN массовые: объявленная
несовместимость классов нарушается в 76–104 случаях, подчинение — в 555–633,
и фильтр помечает 624–709 матчей из 986 (63–72%). Характерный пример —
`cmt#Person` и `cmt#Preference` объявлены несовместимыми, а LaBSE отправляет
их в `confof#Person` и `confof#Volunteer`, где второй класс — потомок первого:
два несовместимых класса получают связанные подчинением образы. Другой
пример — несохранение подчинения: `cmt#Author ⊑ cmt#ConferenceMember`,
но LaBSE отображает их в `confof#Author` и `confof#Member`, где нужная
связь отсутствует; это не доказывает инверсию.

Несохранение подчинения проверяется по непосредственным связям источника,
когда оба их конца сопоставлены, и по транзитивному подчинению в цели.
Отсутствие связи в цели даёт предупреждение: в открытом мире OWL отсутствие
явного знания не является отрицанием отношения. Проверка несовместимости
работает в обе стороны по объявленным парам классов, но не заменяет reasoner
для остальных аксиом.
У LLM доля помеченных матчей ниже (2.7–18.8%), однако здесь сравниваются
уже отфильтрованные по уверенности LLM-ответы по 84 записям и
эмбеддинговые результаты без порога по 21 записи с иным объёмом предсказаний. Числа не доказывают,
что LLM чище калиброванных эмбеддингов.

#### 6.4.3. Проверка как фильтр

Флаги используются как фильтр: помеченные пары выбрасываются, метрики
пересчитываются. В скобках — число записей, где фильтр улучшил и ухудшил F1.
Precision и recall флага посчитаны pooled, то есть по всем матчам подхода, а не
средним по записям: у LLM-подходов большинство записей не помечают ничего, и
среднее по ним занижало бы precision.

Для LLM F1 здесь усреднён по 84 записям C/CP/CC/ENS, а не только по ансамблю,
поэтому исходные значения отличаются от таблиц разделов 6.1 и 6.4.4.
«Без фильтра» означает отсутствие дополнительного семантического фильтра;
основной фильтр уверенности LLM уже применён.

Отсечение одних ошибок (нарушений 1:1 и несовместимости) снижает F1
эмбеддингов и GNN на 0.004–0.035; флаги могут удалять и верные матчи.
У deepseek + MiniLM есть небольшое улучшение, у остальных LLM — ноль или снижение.
Отсечение ошибок вместе с предупреждениями повышает F1 у эмбеддинговых
подходов и GNN на 0.023–0.068 (LaBSE 0.360 → 0.419,
MiniLM 0.349 → 0.418), а у LLM-подходов снижает на 0.006–0.028.

0.86–0.89; базовая доля неверных матчей в тех же отображениях — 0.78–0.83.
Это слабое обогащение ошибками (+0.06…+0.09), не надёжный критерий
отбрасывания каждой отдельной пары. У LLM базовая доля ошибок — 0.12–0.50,
precision флага — 0.20–0.62; небольшой объём помеченных пар и ложные
срабатывания ограничивают полезность фильтра.

Отдельно про «низкую уверенность»: как самостоятельная проверка она не
существует. Число помеченных ею матчей совпадает с первым шагом развёртки по
порогу из §6.4.4 — это параметр постобработки, а не согласованностный сигнал, и
как результат проверки он больше не приводится. У LLM-подходов она и не может
сработать: пайплайн публикует только пары с уверенностью больше 0.7, поэтому
при пороге 0.7 не отбрасывается ни одна из 522, 568, 639 и 1241 пары.
Практический вывод: проверка согласованности работает как отчёт для оператора и
как постобработка слабого матчера, но не как универсальный фильтр.
Совместный эффект калиброванного порога и семантических флагов не измерялся.

#### 6.4.4. Калибровка порога уверенности

Отсечение по уверенности исследовано как самостоятельный этап.
Сетка порогов — $0.0, 0.1, \ldots, 0.9, 0.95, 0.99$.
Порог выбирается по среднему F1 остальных 20 пар, при равенстве —
меньший порог. Сохраняются пары с уверенностью **не ниже** выбранного значения.
Здесь фильтруются уже сохранённые инъективные предсказания, а не заново
решается задача назначения по всей матрице кандидатов.
Для LLM в таблице используется ансамбль, уже прошедший основной порог 0.7;
«до дополнительного порога» не означает нефильтрованные решения LLM.

у rubert-base (0.885). Диапазоны сходства различаются, но сами по себе
не объясняют причин различий качества.

macro precision и recall. Для сравнения pooled F1 из `results/consistency/stats.json`:
LaBSE без порога — 0.346, после LOO — 0.623; ruRoberta-large после LOO —
0.664; StringEquiv — 0.637. Pooled-метрики суммируют TP, FP и FN по парам
и сильнее зависят от размера каждого отображения.

Во-вторых, единый порог между моделями не переносится. Порог 0.7 из
LLMs4OM у LaBSE отсекает 680 пар из 986, а у ruRoberta-large не срабатывает
вообще: ни одно из её 986 сходств не ниже 0.70, и первые потери появляются
лишь при 0.80 (956 пар из 986). Именно поэтому в работе порог
калибруется под модель, а не берётся общим: оптимум зависит и от модели, и от
пары — у LaBSE он лежит в диапазоне 0.70–0.90, у MiniLM 0.80–0.90,
у rubert-base и ruRoberta-large 0.95.

#### 6.4.5. Потолок отбора кандидатов

LLM классифицирует только $k$ кандидатов, предложенных ретривером, поэтому
эталонная пара, не попавшая в кандидатное множество, невосстановима при любом
качестве модели. Полнота кандидатного множества задаёт потолок для всего
LLM-подхода:

| Ретривер                 | $k=1$ | $k=2$ | $k=3$ | $k=5$ | $k=10$ | Пусто | F1 max |
|--------------------------|:-----:|:-----:|:-----:|:-----:|:------:|:-----:|:------:|
| MiniLM (полное описание) | 0.555 | 0.662 | 0.747 | 0.783 | 0.866  | 0.0%  | 0.878  |
| BM25                     | 0.687 | 0.720 | 0.722 | 0.730 | 0.733  | 22.8% | 0.844  |
| BM25 + эмбеддинги        | 0.809 | 0.866 | 0.909 | 0.927 | 0.956  | 0.0%  | 0.978  |

Источник — `results/consistency/retrieval.json`; recall и доля источников без
кандидатов усреднены macro по 21 паре. Это отдельная диагностическая
развёртка retrieval, не восстановленные кандидатные списки исторических LLM-запросов.
Последняя колонка использует диагностический бюджет: пять кандидатов у
MiniLM и BM25, десять у гибрида. Формула $2R/(1+R)$ при macro recall $R$
даёт верхнюю оценку macro F1: предполагается precision = 1.0 и не учитывается
ограничение 1:1. Она не гарантирует достижимость этой оценки.

Гибридный ретривер покрывает 92.7% эталона при $k = 5$ (потолок F1 0.962),
а при $k = 10$ — 95.6% (потолок 0.978). В LLM-прогоне гибрид объединяет
два списка по пять, то есть имеет бюджет до десяти кандидатов; остальные
ретриверы — пять. При пяти MiniLM покрывает 78.3% (потолок 0.878).
Разрыв до потолка оставляет место улучшению классификации, но отбор
остаётся ограничением. Развёртка по $k$ измеряет только чувствительность
ретривера: новых LLM-прогонов с разными $k$ здесь нет.

Отсюда же ответ на вопрос о чувствительности к $k$: у эмбеддингового отбора
полнота продолжает расти до $k = 10$ (0.783 → 0.866), а у BM25 почти
насыщается (0.730 → 0.733), потому что документ там — только имя класса.
Слабое место BM25 видно и в другом: для 22.8% эталонных исходных узлов он не
находит ни одного кандидата с ненулевым счётом, и эти пары теряются до
обращения к модели.

бенчмарку не оценён на независимом наборе данных.

#### 6.4.7. Разброс генерации LLM

Прогоны LLM недетерминированы, поэтому одна и та же конфигурация (гибридный
ретривер, режим C, deepseek-v4-flash) выполнена трижды на двух парах
(`uv run -m src.runners.repeats`). Повторные прогоны не пишутся в кэш результатов,
чтобы не подменять опубликованные числа.

| Пара                | Прогон 1 | Прогон 2 | Прогон 3 | Среднее | $\sigma$ | Размах |
|---------------------|:--------:|:--------:|:--------:|:-------:|:--------:|:------:|
| cmt ↔ confOf        | 0.750    | 0.533    | 0.625    | 0.636   | 0.109    | 0.217  |
| confOf ↔ conference | 0.556    | 0.600    | 0.588    | 0.581   | 0.023    | 0.044  |

Источник — `results/llm-variance.json`; $\sigma$ — выборочное стандартное
отклонение трёх результатов, не стандартная ошибка среднего по бенчмарку.


Измеренный размах подтверждает недетерминизм этих двух пар в режиме C.
Он не оценивает шум среднего по бенчмарку и не проверяет устойчивость
ансамбля. Отсутствие значимости в парном тесте также не означает,
что все различия являются шумом.

### 6.5. Дополнительный эксперимент Jev

**Вопрос.** Можно ли заменить генерацию JSON-ответа LLM моделью,
возвращающей вероятности решений, сохранив схему «retrieval → оценка пар →
порог → отбор 1:1»? Это проверка ещё одного классификатора, не новый метод
сопоставления и не замена проверки согласованности.

**Протокол.** Четвёртого октября 2026 года через OpenRouter Decisions API [10]
запущен `typesafe/jev-1.13`; во всех ответах записана версия
`typesafe/jev-1.13-20260917`, провайдер TypeSafe. Кандидаты сохраняются
существующим `HybridLLMMatcher`: MiniLM `name_only` top-5 и BM25 top-5,
объединение до десяти кандидатов. Тексты C/CP/CC берутся из прежнего
`LLMMatcher._describe_concept`. Для каждого кандидата независимый вопрос
`Noul` [11] спрашивает об эквивалентности классов, исключая просто
связанность и отношение подкласса/надкласса. Возвращается вероятность «да»,
а не самооценка `confidence` внутри сгенерированного текста.

Все вероятности сохраняются до постобработки. Сначала оставляются кандидаты
с вероятностью **строго выше** порога, затем выполняется `greedy_injective`
по всему оставшемуся набору. При ошибке API сбор останавливается с сохранением
журнала, embedding fallback отсутствует. Сетка порогов — от нуля до 0.95
с шагом 0.05, затем 0.99 и 1.0; при равенстве среднего F1 выбирается меньший
порог. Порог и, для итогового результата, представление выбираются на остальных
20 парах. Ансамбль использует прежнее голосование «не менее двух из трёх»
с одним общим LOO-порогом, выбранным по F1 ансамбля.

Источник таблицы — `results/jev-experiment.json`; все метрики macro по 21 паре.

| Режим    | F1 при 0.7 | P LOO | R LOO | F1 LOO |
|----------|-----------:|------:|------:|-------:|
| C        | 0.448      | 0.625 | 0.630 | 0.612  |
| CP       | 0.287      | 0.697 | 0.706 | 0.690  |
| CC       | 0.328      | 0.528 | 0.697 | 0.590  |
| Ансамбль | 0.393      | 0.635 | 0.713 | 0.658  |

Все 21 разбиение выбирают для CP порог 0.25; совместный выбор представления
и порога также выбирает CP во всех разбиениях и даёт F1 = 0.690.
Это не oracle-выбор по эталону оцениваемой пары. Pooled-результат:
176 верных соответствий из 255 предсказаний на 258 эталонных,
precision = 0.690, recall = 0.682, F1 = 0.686.
Перенос порога 0.7 даёт заметно худшее качество; ансамбль после LOO уступает CP.

**Сравнение.** В отдельной новой семье из девяти сравнений применены
парный bootstrap и критерий Уилкоксона с поправкой Холма. Для итогового
совместного LOO-выбора результаты относительно прежних баз:

| База                           | Δ F1 (Jev − база) | 95% ДИ           | $p$ Холм | В/Н/П  |
|--------------------------------|------------------:|------------------|---------:|--------|
| StringEquiv, 0.663             | +0.027            | [−0.036, +0.092] | 1.00     | 12/0/9 |
| ruRoberta-large + LOO, 0.677   | +0.013            | [−0.032, +0.055] | 1.00     | 12/1/8 |
| Гибридная LLM, ансамбль, 0.645 | +0.045            | [−0.018, +0.110] | 1.00     | 12/1/8 |

Численно Jev выше, но превосходство не подтверждено. Напротив, при фиксированном
пороге 0.7 все одиночные представления Jev хуже соответствующих исторических
LLM-режимов после поправки Холма ($p \leq 0.0046$). Это результат
сравнения конкретных протоколов, не доказательство непригодности модели.
Прежняя семья из двенадцати сравнений (раздел 6.4.6) не объединялась с новой;
обе семьи имеют исследовательский характер. Зависимость пар через общие
онтологии остаётся ограничением статистики.

**Кандидаты и расходы.** Для каждого режима сохранено 6318 пар-кандидатов:
в них попали 236 из 258 эталонных соответствий (pooled recall = 0.915).
Это не macro recall диагностической развёртки раздела 6.4.5 и не итоговая
полнота матчера. По 21 паре требуется 1216 обработок исходного класса
(одни и те же классы повторяются в разных парах); три режима дают 3648
запросов. Все успешны, без повторных попыток; стоимость по `usage.cost` —
$0.129266424, с отдельной проверкой доступа — $0.129285954.
Медиана запроса — 0.273 секунды, p95 — 0.367 секунды.
Это измерения данного клиента и провайдера, не сравнение скорости с прежними LLM.

**Проверка вероятностей.** Для CP на всех кандидатах до отбора Brier = 0.0235,
ECE по десяти равным интервалам = 0.0477; Brier постоянного отрицательного
ответа — 0.0374. Brier — средний квадрат ошибки вероятности относительно
метки, ECE — взвешенное по числу кандидатов расхождение средней вероятности
и доли положительных меток в интервалах. Отсутствие пары в эталоне считается
отрицательной меткой, хотя эталон может быть неполон. Низкие значения
не гарантируют правильность отдельного решения или калибровку на другом домене.

**Воспроизводимость и ограничения.** `experiments/jev/manifest.json`
содержит кандидаты, тексты, версии пакетов и SHA-256 данных;
`requests.jsonl` — реальные запросы, ответы и расходы без ключа доступа;
`collection-sources.tar.gz` — исходники подготовки и сбора на момент прогона.
Команда `uv run --no-sync python -m src.runners.jev_evaluate`
пересчитывает метрики без сети и оплаты. Этот отчёт отдельный:
`make compare` и проверка 483 канонических записей не включают Jev;
семантические флаги для его отображений здесь не оценивались.

Прежние LLM-кэши получены в другое время и не содержат всех кандидатов,
решений до отбора и признаков fallback. Сохранены алгоритм retrieval,
настройки и тексты, но идентичность исторических списков кандидатов проверить
нельзя. Инструкция уточнена с «same entity» до явной эквивалентности классов,
поэтому эффект только архитектуры модели не изолирован.
Это один полный прогон; устойчивость результата и снижение вариативности
не проверены. Открытые аналоги, включая Laya, не запускались.

## 7. Выводы

### 7.1. Итоги

Разработан экспериментальный прототип автоматического сопоставления таксономий:
четыре основных подхода (эмбеддинговый, строковый, генеративная LLM по мотивам
LLMs4OM и Siamese GraphSAGE), кэширование результатов, визуализация
и модуль частичной структурной проверки. Дополнительно проверен классификатор
Jev с сохранением вероятностей и расходов. Все основные сравнения охватывают
21 пару семи онтологий Conference и 258 загруженных эталонных соответствий.
Вклад работы — реализация, адаптация и проверяемый экспериментальный анализ,
а не изобретение задачи сопоставления или доказанное превосходство над
существующими системами ontology matching.

Отображение таксономий (средний F1 по 21 паре):

- **Jev с совместным LOO-выбором представления и порога — 0.690.**
  Наибольшее наблюдаемое среднее среди рассмотренных конфигураций,
  но превосходство над строками, ruRoberta-large с порогом и гибридным
  LLM-ансамблем статистически не подтверждено. Независимых повторов нет;
  эксперимент не изолирует эффект архитектуры (раздел 6.5).
- **Лучший генеративный LLM-ансамбль — гибрид, 0.645**; с BM25-ретривером
  0.624, с обычным MiniLM-ретривером 0.602 (deepseek-v4-flash) и 0.575
  (gpt-4.1-mini). Это ниже строкового baseline (0.663) и ниже лучшего
  откалиброванного эмбеддингового результата (0.677). Потенциальная
  полезность LLM как дополнения к строкам требует отдельной проверки.
- **StringEquiv (baseline) — 0.663**: строковое совпадение имён
  конкурентоспособно на парах с общей лексикой (до F1 = 1.000
  на `cmt ↔ edas`) и остаётся обязательной точкой отсчёта.
- **Калибровка порога важнее выбора модели.** С порогом, подобранным по схеме
  leave-one-pair-out, ruRoberta-large даёт 0.677, MiniLM 0.653, rubert-base
  0.646, LaBSE 0.636 — без порога соответственно 0.299 / 0.349 /
  0.285 / 0.360. Порог подбирается под модель (0.70–0.90 у LaBSE, 0.80–0.90
  у MiniLM, 0.95 у rubert-base и ruRoberta-large): единое значение не
  переносится, потому что косинусные сходства разных моделей лежат в разных
  диапазонах.
- **Представление узла влияет на качество MiniLM.** На этих 21 парах
  при правиле `argmax` имя даёт 0.309, полное описание — 0.211.
  Имя с цепочкой предков даёт 0.303, с атрибутами — 0.280,
  с атрибутами, несовместимостями и комментарием — 0.190. Отдельный эффект
  несовместимостей и комментария не изолирован. Это результат
  конкретной абляции, не универсальный запрет на структурный контекст.
- **GNN — 0.333 без порога против 0.349 у MiniLM-базы.** Это отрицательный
  результат только без отсечения: с LOO-порогом GNN даёт 0.667, база 0.653.
  Парного теста нет, поэтому значимое превосходство не установлено.
  Причины различий протоколов (0.314 без свёрток, 0.318 при отложенной
  онтологии) остаются гипотезами, а не доказательством непереносимости структуры.

Проверка согласованности:

- **Целостность таксономий.** Реализованные проверки не нашли нарушений
  в 491 классе семи онтологий. Самопроверка на испорченных данных
  подтверждает срабатывание проверок; достижимость автоматически
  определённого корня дублирует последствия циклов и оборванных ссылок.
  Нулевой отчёт не доказывает OWL-согласованность.
- **Согласованность отображений.** В сохранённых результатах всех подходов
  инъективность 1:1 выполняется, поэтому
  содержательны проверки объявленной несовместимости и несохранения
  подчинения, включая отсутствие нужной связи в цели. Числа раздела 6.4.2
  сравнивают эмбеддинговые результаты без порога (21 запись) с уже отфильтрованными LLM
  (84 записи); меньшая доля флагов у LLM не доказывает превосходства
  над калиброванными эмбеддингами.
- **Проверка как фильтр.** Главный эффект даёт не семантическая проверка,
  а отсечение по уверенности: порог, подобранный по схеме leave-one-pair-out,
  поднимает F1 эмбеддинговых подходов с 0.360 до 0.636 (LaBSE) и до 0.677
  (ruRoberta-large). Фильтр по ошибкам и предупреждениям повышает F1
  эмбеддинговых отображений без порога и снижает F1 генеративных LLM.
  Это измерение этих выходов, не правило «слабым помогает, сильным вредит»;
  совместное применение порога и семантического фильтра не проверено.
- **Потолок отбора кандидатов.** Гибрид при $k = 5$ покрывает 92.7%
  эталона (потолок F1 0.962), при $k = 10$ — 95.6% (0.978).
  Реальный гибридный LLM-прогон имеет до десяти кандидатов, остальные — пять:
  MiniLM покрывает 78.3%, BM25 73.0%. Это чувствительность ретривера,
  а не измерение LLM при разных бюджетах; отбор остаётся ограничением.
- **Статистика основных методов.** В прежней семье из двенадцати сравнений
  после поправки Холма значимы только два:
  превосходство строк над BM25-LLM в среднем по режимам (−0.059,
  Holm $p = 0.013$) и эффект порога LaBSE (+0.276, Holm $p < 0.0001$).
  Разница лучшего LLM-ансамбля и строк не подтверждается (−0.018,
  Holm $p = 1.00$), как и ruRoberta-large с порогом и строк (+0.014,
  Holm $p = 1.00$; восемь побед, девять поражений).
  Средние приводятся как ориентир, а не как доказанное преимущество.

Для генеративных LLM выбор режима зависит от конфигурации; ансамбль
фиксирует агрегацию без выбора по эталону, но снижение шума не измерено.
У Jev на этих данных совместный LOO-выбор всегда выбирает CP.
Универсальный лучший режим на других данных из этих наблюдений не следует.

### 7.2. Ограничения

- **Проверки согласованности неполны.** Реализованы проверки на графе и на
  объявленной несовместимости, но не формальный вывод: гибридная схема с
  reasoner (HermiT, Pellet) для OWL-аксиом, как предполагал исходный замысел,
  не реализована. Полнота проверки ограничена разметкой самих онтологий: если
  несовместимость не объявлена (в `sigkdd` её нет ни у одного класса),
  соответствующие нарушения не обнаруживаются.

- **Разброс генерации измерен на двух парах, а не на всех.** Три повторных
  прогона одной конфигурации (раздел 6.4.7) дают размах до 0.217 внутри пары.
  Полных повторов всех пар и режимов нет, поэтому шум среднего по
  бенчмарку и ансамбля не оценён.
  У Jev выполнен один полный прогон; его устойчивость также не оценена.

- **Порог калибруется на том же бенчмарке.** Схема leave-one-pair-out
  исключает подгонку под отложенную пару, но и сетка порогов, и сами 21 пара
  взяты из одного набора OAEI; перенос порога на другой бенчмарк не проверялся.
  Также выбор лучшей эмбеддинговой модели выполнен по результатам этого
  бенчмарка, а не на независимой выборке.

- **Парсер извлекает лишь часть ограничений свойств.** В подготовленном JSON
  атрибуты есть у пяти классов `conference`, у одного `edas`, у пятнадцати
  `iasted` и у семи `sigkdd`; у `cmt`, `confOf` и `ekaw` их нет.
  Это не утверждение об отсутствии ограничений в исходном OWL:
  ограничения `subClassOf` и вложенные выражения не извлекаются.
  Сценарий `attribute` для `cmt` проверяет добавление атрибутов с нуля.

- **Масштабируемость.** Одно обращение классифицирует до $k$ кандидатов
  одного узла-источника. До повторов требуется не более
  $3\lvert S\rvert$ запросов на пару и три представления;
  BM25 пропускает источники без положительных кандидатов.
  Токены растут как $O(k\lvert S\rvert)$: для `cmt` и пяти кандидатов
  во всех режимах это 87 первичных запросов и 435 суждений о парах.
  Blocking сокращает кандидатов и токены, но не число per-source вызовов
  сам по себе. Дополнительное пакетирование источников не реализовано.

- **GNN: промежуточные варианты не записаны.** Записи пяти протоколов раздела
  6.3 собраны в `results/gnn-protocols.json` (команда, конфигурация, число
  фолдов, макро-метрики и F1 по каждой паре), а полные записи с `match_pairs`
  есть только у основного протокола `pair-loo` — в `results/gnn/*.json`:
  остальные протоколы пишут в тот же каталог и перезаписывают друг друга,
  от них остаются чекпойнты `fold-onto-*.pt`. Числа промежуточных
  архитектурных вариантов воспроизвести нельзя: их прогоны в кэш не
  сохранились.

- **Размер датасета.** Семь онтологий и 21 пара — маленький полигон;
  синтетические вариации порождаются из каждой онтологии, встречающейся
  источником в обучающих парах, но их польза ограничена: вариация — это та же
  онтология с переименованными идентификаторами, новых концептов она не
  добавляет.

- **Перенос на другой домен не проверялся.** Основной `pair-loo`
  оценивает сопоставление уже виденных онтологий: обе онтологии отложенной
  пары остаются концами других обучающих пар. Протокол `ontology-loo`
  исключает отложенную онтологию и связанные с ней синтетические варианты,
  но остаётся внутри предметной области Conference (раздел 6.3).

- **Эмбеддинговые модели не дообучались.** Использованы предобученные
  LaBSE, MiniLM-L6-v2, ruRoberta-large и rubert-base; дообучение на парах
  OAEI не проводилось, поэтому резерв «подстроить модель под задачу» не
  исчерпан. При этом LaBSE с порогом (0.636) ниже гибридного LLM-ансамбля
  (0.645), а ruRoberta-large с порогом (0.677) выше всех LLM-ансамблей по среднему.

- **Итоговая чувствительность LLM и Jev к бюджету кандидатов не измерена.**
  Развёртка recall@$k$ касается только retrieval. Новых классификационных
  прогонов при разных $k$ нет; бюджеты MiniLM/BM25 и гибрида различаются.

- **Нет сравнения с полноценными системами OM.** AML, LogMap и другие
  классические системы сопоставления таксономий не запускались.
  Геоинформационные системы служат мотивацией, но качество на их таксономиях,
  на русскоязычных данных и при участии эксперта в этой работе не оценивалось.

### 7.3. Перспективы

1. **Формальный вывод поверх реализованных проверок.** Гибридная схема с
   reasoner (HermiT, Pellet) для OWL-аксиом плюс LLM для семантически
   подозрительных связей — то, что проверки на графе и на объявленной
   несовместимости не покрывают.

2. **Оценка устойчивости и переноса.** Повторить полные прогоны LLM и Jev,
   оценить чувствительность классификации к $k$, затем проверить перенос
   на другой домен и сравнить с полноценными системами OM.

3. **Масштабирование LLM-подхода.** Blocking сокращает кандидатные списки,
   но не число per-source вызовов. Для уменьшения числа запросов требуется
   отдельная схема пропуска источников или пакетирования нескольких
   источников в одном запросе.

4. **Согласованная постобработка.** Сравнить глобальный жадный отбор
   с оптимальным назначением (например, венгерским алгоритмом),
   а также измерить совместный эффект порога и семантических флагов.
   Пороги должны калиброваться отдельно под модель, а не навязываться
   одним числом шкалам с разным смыслом.

5. **GNN на бо́льших данных.** Тестирование GraphSAGE и GAT на расширенном
   наборе онтологий (сотни, например BioPortal) с записью конфигурации
   в кэш.

6. **Интерактивный Human-in-the-Loop.** Интерфейс поверх готовых материалов:
   проверки выдают список нарушений с указанием пары и причины, а режим с
   порогом и списком неуверенных пар (`match_with_threshold`) отделяет случаи
   для ручного разбора.

## Что изменилось после первой защиты

После первой защиты сравнение подходов было перепроверено, и в нём нашлись три
несогласованности, из-за которых прежние выводы были смещены в пользу LLM. Все три
устранены, числа пересчитаны.

1. **Единое правило отбора пар.** Раньше подходы считались разными правилами:
   эмбеддинговые выдавали по одному соответствию на каждый *исходный* узел
   (с коллизиями по цели), GNN-матчер оценки — по одному на каждый *целевой*,
   а LLM — жадно-инъективное отображение 1:1, так что колонки сравнительной
   таблицы были несопоставимы.
   Теперь эмбеддинги, GNN и LLM используют общее жадно-инъективное правило
   (`src/matching_rules.py`); StringEquiv остаётся точным строковым baseline.
   Варианты правила приведены отдельной абляцией (раздел 5.3).
2. **Честная агрегация LLM.** В прежних таблицах строка LLM была максимумом по трём
   представлениям, выбранным по эталону оцениваемой пары, а «ансамбль» — максимумом
   по четырём конфигурациям. Теперь публикуются числа без выбора по паре: среднее по
   режимам, выбор режима по схеме leave-one-pair-out и ансамбль по правилу «не менее
   двух из трёх» (раздел 4.3).
3. **Проверяемый негативный результат по GNN.** Обучение и оценка сохраняют
   конфигурацию и сиды, матчер оценки исправлен, добавлен протокол с полностью
   отложенной онтологией (раздел 6.3).

Дополнительно: проверки согласованности, метрики и правила отбора покрыты
юнит-тестами (`make test`), а абляция режима описания, потолок отбора
кандидатов и парные тесты вынесены в воспроизводимые команды (`make ablation`,
`make retrieval`, `make stats`); состав каждого подхода (модель, параметры,
дата) собирается командой `make provenance` в `results/provenance.json`.

Основные кэши обновлены 2026-09-27; отдельный эксперимент Jev выполнен
2026-10-04 и не подменяет эти записи. `results/provenance.json` различает
константы текущего кода, поля реальных записей и даты изменения файлов.
Дата изменения файла не доказывает время API-вызова, а константа кода —
версию модели, фактически ответившей при историческом прогоне.
Полная версия Jev и каждый его ответ сохранены в отдельном журнале.
