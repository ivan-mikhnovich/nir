# Автоматическое отображение между таксономиями

Курсовая работа (НИР) по теме «Разработка средств автоматического отображения между
таксономиями и проверки их согласованности».

В работе реализовано автоматическое построение соответствий (маппинга) между узлами
двух таксономий, оценка уверенности в найденных соответствиях и проверка
семантической согласованности — как внутри каждой таксономии, так и в построенном
отображении. Пайплайн сравнения, разбор результатов и ограничения — в пояснительной
записке (`note.md`).

## Данные

OAEI 2025 Conference track: семь онтологий (`cmt`, `confOf`, `conference`, `edas`,
`ekaw`, `iasted`, `sigkdd`, от 29 до 140 классов) и 21 эталонный alignment
(только классовые соответствия). Из онтологий берётся лишь иерархия `subClassOf` —
таксономия. Дополнительно генерируются синтетические вариации `cmt`: точные,
синонимичные, структурные и атрибутные.

## Подходы

1. **Эмбеддинги.** Описание узла превращается в вектор bi-encoder'ом, кандидаты
   отбираются по косинусному сходству (top-k). Модели: LaBSE, MiniLM-L6-v2,
   ruRoberta-large, rubert-base.
2. **LLM** (по мотивам LLMs4OM, arXiv:2404.10317). Бинарная классификация пар
   кандидатов в трёх представлениях: C (имя класса), CP (имя + родители),
   CC (имя + дети), а также ансамбль трёх режимов. Модели: `gpt-4.1-mini`,
   `deepseek-v4-flash`. Кандидаты отбираются эмбеддингами, BM25 или объединением
   обоих (см. ablations ниже).
3. **StringEquiv** — нижняя граница OAEI: регистронезависимое совпадение меток.
4. **GraphSAGE** — сиамская графовая сеть на структурных признаках узла
   (отрицательный результат, см. ниже).
5. **Проверка согласованности** (`src/consistency.py`) — целостность таксономии
   (циклы `is-a`, совпадающие метки, несовместимость класса с предком, классы без
   пути к корню) и согласованность отображения (инъективность 1:1, противоречие
   объявленной несовместимости, инверсия подчинения, низкая уверенность).

## Результаты

Среднее F1 по 21 паре OAEI, посчитанное по кэшу `results/`; для LLM — лучшее из
трёх представлений узла (C, CP, CC; ансамбль не учитывается):

| Подход | Среднее F1 |
|---|---:|
| LaBSE с порогом 0.90 (leave-one-pair-out) | 0.688 |
| LLM + гибридные кандидаты (deepseek-v4-flash) | 0.685 |
| MiniLM-L6-v2 с порогом 0.90 | 0.670 |
| StringEquiv (baseline) | 0.663 |
| LLM + BM25-кандидаты (deepseek-v4-flash) | 0.662 |
| rubert-base с порогом 0.95 | 0.646 |
| LLM + MiniLM-кандидаты (deepseek-v4-flash) | 0.644 |
| ruRoberta-large с порогом 0.99 | 0.643 |
| gpt-4.1-mini с порогом 0.90 | 0.639 |
| LLM + MiniLM-кандидаты (gpt-4.1-mini) | 0.610 |
| LaBSE без порога | 0.323 |
| MiniLM-L6-v2 без порога | 0.314 |
| ruRoberta-large без порога | 0.279 |
| rubert-base без порога | 0.258 |
| GNN (Siamese GraphSAGE) | 0.204 |
| Сырой MiniLM с тем же матчером, что у GNN (`--baseline`) | 0.156 |

Разбивка по парам — в `results/comparison.xlsx` (листы по подходам), полные
таблицы и анализ — в `note.md`, раздел 6.

Основные наблюдения:

- Описывать узел нужно **только именем класса**. Путь от корня и атрибуты снижают
  F1 в полтора раза (0.314 против 0.207 у MiniLM): BERT-модели не различают
  одинаковые имена на разных ветвях иерархии, поэтому `name_only` — режим
  по умолчанию (`src/matchers/embedding.py`).
- LLM выигрывает у строкового baseline на парах с низким лексическим перекрытием
  (например, `cmt` ↔ `conference`: 0.640 против 0.375) и почти не даёт выигрыша
  там, где метки совпадают дословно (`confOf` ↔ `conference`: 0.762 против 0.737).
- Ретривер кандидатов влияет на результат сильнее, чем выбор режима представления
  узла: у DeepSeek замена обычного MiniLM-ретривера на BM25 даёт 0.644 → 0.662,
  на гибридный (MiniLM ∪ BM25) — 0.644 → 0.685.
- GNN при одинаковой постобработке улучшает сырые эмбеддинги (0.156 → 0.204,
  лучше на 14 парах из 21), но уступает основному эмбеддинговому подходу
  (0.204 против 0.314): 20 обучающих пар мало, чтобы выучить структуру,
  переносимую между онтологиями.
- Прогоны LLM недетерминированы: два запуска одной конфигурации дают разный F1,
  поэтому различия на уровне 0.02–0.05 по отдельным парам — шум, а выводы
  делаются по средним и по числу побед.
- **Калибровка порога уверенности важнее выбора модели.** Без порога
  эмбеддинговый матчер берёт ближайшего кандидата на каждый исходный узел и
  выдаёт 1195 пар на 258 эталонных; отсечение по порогу, подобранному на других
  парах (leave-one-pair-out), поднимает F1 LaBSE с 0.323 до 0.688. Единый порог
  между моделями не переносится: сходства ruRoberta-large не опускаются ниже 0.73.
- **Средние надо проверять парными тестами.** Разница между лучшей
  LLM-конфигурацией и StringEquiv статистически неотличима от нуля (−0.001,
  p = 1.00): LLM выигрывает на одних парах и проигрывает на других. LaBSE с
  порогом обходит StringEquiv значимо (+0.025, p = 0.020). Три повторных
  прогона одной конфигурации дают размах до 0.173 внутри одной пары
  (`results/llm-variance.json`) — это шире межподходных различий, поэтому
  выводы делаются по 21 паре, а не по отдельным парам.
- **Проверка согласованности** находит у LLM-отображений единицы нарушений
  объявленной несовместимости (1–24 на весь бенчмарк), тогда как эмбеддинговые
  отображения нарушают её в 328–424 парах и нарушают 1:1 в 245–255; пример —
  несовместимые `cmt#Acceptance` и `cmt#Rejection`, оба отправленные LaBSE
  в `confof#Reception`. Как фильтр проверка полезна только по уверенности.
- **Узкое место LLM — классификация, а не отбор кандидатов.** Полнота
  кандидатного множества при k = 5: гибрид 0.927 (потолок F1 0.962),
  эмбеддинги 0.780, BM25 0.730, причём BM25 не даёт кандидатов для 22.8%
  эталонных узлов.

## Запуск

Нужны Python ≥ 3.14, [uv](https://docs.astral.sh/uv/) и (для `make docx`)
pandoc ≥ 3.0.

```bash
make download        # скачать онтологии OAEI и эталонные alignment'ы
make prepare-data    # OWL -> JSON-таксономии + синтетические вариации
make run-embedding   # эмбеддинговый эксперимент (LaBSE)
make run-string-equiv
make compare-full    # embedding + StringEquiv на всех 21 паре + сводная таблица
make consistency     # проверки согласованности, фильтр и развёртка по порогу
make viewer          # интерактивный просмотрщик таксономий (tkinter)
make viz             # .dot для всех таксономий и пар -> results/viz/
make docx            # note.md -> note.docx
make lint            # ruff
```

LLM-эксперименты требуют ключей и запускаются отдельно: `make run-llm`
(`KODIKROUTER_API_KEY`), `make run-llm-deepseek` (`DEEPSEEK_API_KEY`),
`make run-llm-local` (локальный llama-swap на `127.0.0.1:12434`). Результаты
кэшируются в `results/`, поэтому повторять их для сборки таблиц не нужно.

## Структура репозитория

```
src/
  taxonomy.py        структуры данных: TaxonNode, Taxonomy, Alignment, TaxonMatch
  owl_parser.py      OWL -> Taxonomy (owlready2)
  data_loader.py     загрузка OAEI, генератор синтетических таксономий
  prepare_data.py    скрипт: OWL -> JSON, синтетика
  metrics.py         precision/recall/F1 для 1:1- и ranked-соответствий
  consistency.py     проверки целостности таксономий и согласованности отображений
  cache.py           единое описание путей кэша результатов
  matchers/          embedding, llm, string_equiv, gnn, bm25_llm, hybrid
  runners/           эксперименты (compare, consistency, stats, retrieval), сводная таблица
  viz/               GraphViz-рендеринг и интерактивный просмотрщик
data/raw/oaei/       7 онтологий и 21 эталонный alignment (скачиваются)
data/processed/      JSON-таксономии и alignment'ы (генерируются)
results/             кэш результатов по подходам и парам, результаты проверок
note.md              пояснительная записка
presentation/        презентация (Beamer)
papers/, books/      статьи и книги, на которые опирается работа
info/Диздок_короткий.md   первоначальный замысел работы
```

## Сгенерированные артефакты

В репозитории лежат готовые `note.docx`, `results/comparison.xlsx`,
`presentation/slides.pdf` и `results/viz/`, чтобы их можно было посмотреть
без запуска пайплайна. Они воспроизводятся целями `make docx`, `make compare`,
`make -C presentation` и `make viz` соответственно.
